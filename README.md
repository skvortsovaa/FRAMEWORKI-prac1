# SmartSpace Monitor

**Сервис мониторинга показателей помещений**

## Назначение проекта
Автоматизация сбора, хранения, анализа и визуализации данных о состоянии окружающей среды в закрытых пространствах. Сервис предназначен для обеспечения комфортных, безопасных и энергоэффективных условий, а также для своевременного предотвращения аварийных ситуаций (например, протечек, задымлений или выхода микроклимата за пределы нормы).

## Целевая аудитория
* **Facility-менеджеры и управляющие недвижимостью:** для контроля состояния офисных центров, ТЦ и жилых комплексов.
* **Администраторы специализированных помещений:** серверных, лабораторий, складов (в т.ч. холодильных), архивов.
* **Владельцы «умных домов» и квартир:** для поддержания идеального микроклимата и контроля безопасности.
* **Службы эксплуатации и технического обслуживания:** для мониторинга работоспособности оборудования и датчиков.

## Описание предметной области
Предметная область охватывает процессы контроля микроклимата и технических параметров в помещениях. Она включает в себя физический уровень (IoT-датчики, передающие телеметрию), уровень сбора данных (шлюзы, брокеры сообщений) и аналитический уровень (интерпретация данных, настройка пороговых значений, реагирование на отклонения). 

Контроль таких параметров, как температура, влажность, уровень CO2, освещенность и качество воздуха, критически важен для здоровья людей, сохранности имущества (например, на складах) и оптимизации энергопотребления зданий.

## Основные сущности
В основе архитектуры системы лежат следующие сущности:

1. **Помещение (Room)**
   * Физическое пространство (комната, офис, серверная, склад).
   * *Атрибуты:* название, тип назначения, площадь, этаж, координаты на плане.
2. **Датчик (Sensor)**
   * Аппаратное устройство, установленное в помещении для сбора данных.
   * *Атрибуты:* уникальный ID, серийный номер, тип подключения, статус (активен/неактивен/ошибка), уровень заряда батареи, привязка к помещению.
3. **Показатель (Metric)**
   * Тип измеряемой физической величины (справочник).
   * *Атрибуты:* название (например, "Температура", "Влажность", "CO2"), единица измерения (°C, %, ppm), минимальное и максимальное пороговое значение (норма).
4. **Значение (Value / Reading)**
   * Конкретное измерение, полученное от датчика в определенный момент времени.
   * *Атрибуты:* временная метка (timestamp), числовое значение, статус (в норме / предупреждение / критично), привязка к датчику и показателю.

## ПР5: веб-интерфейс на Django

К консольной версии добавлены проект `smartspace_web` и четыре приложения:
`homepage`, `rooms_web`, `sensors_web`, `reports_web`.
Маршруты разделены между корневым `urls.py` и `urls.py` приложений.

Выполнены общий HTML-каркас, навигация, собственная страница 404
и отображение помещений, датчиков и истории проверок из JSON
(пункты 5.4.6–5.4.8 практической работы).
Функция `page(title, content)` в `homepage/views.py` формирует полный
HTML-документ с `lang="ru"`, UTF-8, `viewport`, заголовком вкладки,
навигацией и Bootstrap 5.3.3 через CDN. Небольшой блок CSS задаёт цвета
страниц; карточки и адаптивная сетка используют классы Bootstrap.
Для загрузки Bootstrap требуется интернет.

| URL | View-функция | Текущее содержимое |
| --- | --- | --- |
| `/` | `homepage.views.index` | Описание и ссылки на разделы |
| `/rooms/` | `rooms_web.views.room_list` | Список объектов Room из JSON и поиск по ID через `?room_id=1` |
| `/rooms/<int:room_id>/` | `rooms_web.views.room_detail` | Помещение и его датчик; 404, если помещения нет |
| `/sensors/` | `sensors_web.views.sensor_list` | Датчики из JSON, доступность, заряд и ссылки на помещения |
| `/reports/` | `reports_web.views.report_list` | История проверок из JSON со статусами |
| `/reports/<str:report_id>/` | `reports_web.views.report_detail` | Снимок проверки; 404, если отчёта нет |

Все страницы возвращают `HttpResponse` с общим оформлением.
Помещения, датчики и отчёты используют объекты ПР3.
Карточки проверяют наличие объекта. Строковый ID отчёта
сохранён в соответствии с форматом ПР3. Прикладные Django-модели и формы
пока не используются; консольная версия и JSON-хранилище сохранены.

Файлы `models.py` пока не содержат прикладных моделей.
Настройки: русский язык, часовой пояс `Europe/Moscow`, `DEBUG = True`
для разработки и разрешённые локальные адреса.

### Данные помещений

`smartspace_web/data.py` содержит функцию `load_project_data()`:
она читает пять файлов `data/{rooms,sensors,metrics,readings,reports}.json`
через `storage.read_json()` и передаёт их в `storage.decode_data()`.
Существующий код ПР3 проверяет данные и восстанавливает ссылки между
объектами в памяти. Путь к данным задаётся относительно `BASE_DIR`,
поэтому не зависит от рабочей папки запуска.

`room_list()` выводит ID, название, этаж и площадь каждого помещения;
название ведёт на карточку. `room_detail()` использует `get_room()` и
`get_room_sensor()` из ПР3. Доступность датчика определяется существующим
методом `Sensor.is_available()`: датчик включён и заряд больше нуля.
Низкий заряд (менее 20%) показывает рекомендацию обслуживания и сам по себе
не делает датчик недоступным. Новые показания при открытии страниц
не генерируются. Названия помещений и строковые ID экранируются для HTML.

На `/rooms/` форма «ID помещения» отправляет GET-параметр `room_id`.
Например, `/rooms/?room_id=1` показывает одно помещение со ссылкой на
карточку; поиск использует существующую `get_room()` из ПР3.
Допускается положительное целое число из цифр 0–9; пробелы по краям
удаляются. Неверный формат и неизвестный ID дают понятное сообщение
на странице поиска с кодом 200. Пустое поле и «Сбросить поиск» показывают
полный список. Значение поля экранируется; поиск не записывает JSON.

Веб-загрузка только читает файлы: `load_data()` с автоматическим откатом
записи и `save_data()` из консольной версии не вызываются.
Повреждённые или отсутствующие файлы, а также наличие `.save-backup.json`
дают страницу «Данные временно недоступны» с кодом 503. Восстановление
прерванного сохранения и миграция прежнего `state.json` остаются в консоли.
Для веб-версии требуется полный текущий набор из пяти JSON-файлов.
Корректный пустой набор показывает сообщение «Помещения пока не добавлены».

### Список датчиков

`sensor_list()` использует тот же `load_project_data()` и отображает
объекты `Sensor`: ID, связанное помещение, активность, заряд и доступность.
Название помещения ведёт на его карточку по `sensor.room.id`.
Доступность вычисляется методом ПР3 `Sensor.is_available()`;
при заряде ниже 20% показывается рекомендация обслуживания.
Например, включённый датчик с зарядом 15% остаётся доступным,
а выключенный или разряженный до 0% — недоступен.

Страница только читает JSON и экранирует названия и ID для HTML.
Корректный пустой набор даёт сообщение «Датчики пока не добавлены».
Ошибки хранилища возвращают общий ответ 503 через
`homepage.views.data_unavailable()` — он используется и помещениями.

### История проверок

`report_list()` читает объекты `Report` и выводит дату, историческое название
помещения и сохранённый статус. Дата ведёт на карточку отчёта. Порядок
соответствует порядку отчётов в JSON. `report_detail()` ищет объект по
строковому ID; отсутствие отчёта даёт оформленный ответ 404 даже при
`DEBUG = True`, ошибки хранилища — общий ответ 503.

Карточка показывает снимок на момент проверки: `room_name`, `sensor_active`,
`battery`, температуру, влажность, протечку и статус. Границы и результаты
анализа берутся из сохранённых `MetricAnalysis`, поэтому последующее
изменение помещения, датчика или текущих норм не переписывает историю.
Ссылка на текущее помещение использует связь `report.room`.
Для недоступного при проверке датчика показания обозначаются «Нет данных».
Все четыре статуса различаются подписями и цветом: НОРМА,
ПРЕДУПРЕЖДЕНИЕ, АВАРИЯ, НЕТ ДАННЫХ. При открытии страниц новые проверки
не запускаются, JSON не меняется; названия и ID экранируются для HTML.

### Установка и запуск веб-версии

Проверенное окружение: Python 3.14.7, Django 5.2.18.
Зависимость `Django==5.2.*` закрепляет ветку из методички.
При первом запуске создать окружение командой `python -m venv .venv`.
Если `.venv` уже существует, повторно создавать его не требуется.
Далее из корня репозитория в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py runserver
```

`migrate` создаёт только встроенные таблицы `admin`, `auth`, `contenttypes`
и `sessions`. Локальный `db.sqlite3` исключён из Git и воссоздаётся этой
командой после клонирования. Помещения, датчики и отчёты остаются в JSON;
переход на Django ORM относится к следующим практическим работам.
Встроенный сервер предназначен для локальной разработки.

Открыть `http://127.0.0.1:8000/`, перейти в «Помещения», открыть карточку
по названию и вернуться к списку. Проверить `/rooms/999/` (если такого ID
нет в данных): должна появиться страница «Помещение не найдено» с кодом 404.
При уменьшении ширины окна карточки располагаются в один столбец.
На `/sensors/` проверить оба датчика, заряд, предупреждение о низком заряде
и переходы по названиям помещений. На `/reports/` открыть отчёт по дате,
проверить показания и переход к помещению, затем возврат в историю.
Адрес `/reports/REP-missing/` для отсутствующего ID должен вернуть 404.

### Проверка собственной страницы 404

В корневом `smartspace_web/urls.py` зарегистрирован обработчик
`handler404 = "homepage.views.page_not_found"`. Он возвращает
`HttpResponse` со статусом **404** и общим HTML-каркасом: навигацией,
сообщением об ошибке и кнопкой «На главную».

В `smartspace_web/settings.py` включён режим разработки `DEBUG = True`;
`ALLOWED_HOSTS = ["localhost", "127.0.0.1"]` сохранён.
Для повторной демонстрации общей страницы 404 временно задать `DEBUG = False`.
Открыть `http://127.0.0.1:8000/nonexistent/` и проверить оформление
страницы. В инструментах разработчика браузера (F12 → Network / Сеть)
обновить страницу: запрос документа `nonexistent/` должен иметь статус 404.
Кнопка «На главную» должна открыть главную страницу с кодом 200.

Адрес `/rooms/abc/` также даёт 404: он не соответствует конвертеру
`<int:room_id>`. Для `/rooms/999/` маршрут существует, но помещение
с таким ID отсутствует: `room_detail()` сам возвращает оформленный ответ
«Помещение не найдено» с кодом 404, в том числе при `DEBUG = True`.

После демонстрации вернуть `DEBUG = True` для дальнейшей разработки.
При `DEBUG = True` Django показывает техническую страницу неизвестного
адреса; собственный обработчик остаётся зарегистрирован и используется
при `DEBUG = False`. Он также обрабатывает исключение `Http404`, если
его возбуждает представление.

## Консольная версия — ПР3: объектная модель

Консольная учебная симуляция мониторинга нескольких помещений.
Показания генерируются случайно; подключения к реальному оборудованию нет.
Основные сущности представлены объектами Python. Программа продолжает
проект ПР2: сохранены все 13 действий меню, JSON-файлы и история проверок.
Перечень атрибутов выше описывает полный сервис; таблица ниже — реализацию ПР3.

### Классы, атрибуты и методы

| Класс | Модуль | Основные атрибуты | Основные методы |
| --- | --- | --- | --- |
| `Room` — помещение | `models/rooms.py` | `id`, `name`, `floor`, `area` | `__init__`, `validate`, `is_on_floor`, `__str__` |
| `Sensor` — датчик | `models/sensors.py` | `id`, `room: Room`, `active`, `battery` | `__init__`, `validate`, `update_state`, `is_available`, `__str__` |
| `Metric` — показатель | `models/metrics.py` | `id`, `name`, `unit`, `minimum`, `maximum` | `__init__`, `validate`, `update_limits`, `analyze`, `__str__` |
| `Reading` — измерение | `models/readings.py` | `id`, `sensor: Sensor`, `metric: Metric`, `report_id`, `measured_at`, `value`, `minimum`, `maximum`, `status` | `__init__`, `validate`, `get_status`, `__str__` |
| `Report` — отчёт | `models/reports.py` | `id`, `room: Room`, `room_name`, `checked_at`, `sensor_active`, `battery`, `temperature`, `humidity`, `leak_detected`, `status` | конструктор dataclass, `__post_init__`, `validate`, `__str__` |

Дополнительные классы:

- `MetricAnalysis` — неизменяемый результат анализа со значением, границами,
  признаком нормы, положением относительно диапазона и отклонением.
- `ProjectData` — контейнер типизированных коллекций `list[Room]`,
  `list[Sensor]`, `list[Metric]`, `list[Reading]`, `list[Report]`.

У четырёх исходных сущностей явно написаны конструкторы `__init__`.
Декоратор `@dataclass` добавляет сравнение по полям и представление для отладки.
У `Report`, `MetricAnalysis` и `ProjectData` он также создаёт конструктор.
Удобный пользовательский вывод пяти сущностей задаётся через `__str__`.

### Взаимодействие объектов

```text
ProjectData
├── rooms:    [Room, ...]
├── sensors:  [Sensor, ...]  ── room ──> Room
├── metrics:  [Metric, ...]
├── readings: [Reading, ...] ── sensor ──> Sensor
│                           └─ metric ──> Metric
└── reports:  [Report, ...]  ── room ──> Room
```

Например, `reading.sensor.room.name` получает название помещения измерения.
Ссылки ведут на те же экземпляры, которые находятся в коллекциях.
В текущей версии у помещения один комбинированный датчик температуры,
влажности и протечки. При добавлении помещения датчик создаётся автоматически.
Измерение также хранит ID отчёта, с которым связано.

Методы `sensor.update_state()` и `metric.update_limits()` сначала проверяют
все новые значения; неудачная операция не меняет прежнее состояние.
`check_room()` использует `sensor.is_available()` и `metric.analyze()`;
результат — объект `Report` и три объекта `Reading` для доступного датчика.

### Что изменилось после ПР2

| Было | Стало |
| --- | --- |
| Списки словарей | Типизированные коллекции объектов в `ProjectData` |
| `room["name"]` | `room.name` |
| ID помещения внутри датчика в памяти | Ссылка `sensor.room` на объект |
| `update_sensor(sensor, active, battery)` | `sensor.update_state(active, battery)` |
| `check_sensor(active, battery)` | `sensor.is_available()` |
| `update_limits(metric, minimum, maximum)` | `metric.update_limits(minimum, maximum)` |
| Расчёт по извлечённым границам | `metric.analyze(value)` |
| Вывод полей словаря | `print(room)`, `print(sensor)`, `print(reading)` |
| `load_data()` возвращает словари | `load_data()` возвращает `ProjectData` с объектами и связями |

Поиск, добавление в коллекции, сортировка и фильтрация остаются обычными
функциями модулей. `monitoring.py` координирует проверку нескольких объектов.
`storage.py` отвечает за внешний формат, `utils.py` — за безопасный ввод.
Преобразование в словари выполняется только на границе JSON в `storage.py`.

### Меню и правила

1. Показать помещения с состоянием датчиков.
2. Добавить помещение и его датчик.
3. Найти помещения по части названия.
4. Отсортировать помещения по площади.
5. Отобрать помещения на этаже.
6. Изменить активность и заряд датчика помещения.
7. Проверить одно помещение.
8. Проверить все помещения.
9. Показать историю отчётов.
10. Показать отдельный список датчиков.
11. Показать справочник показателей и текущие нормы.
12. Изменить норму температуры или влажности по ID показателя.
13. Показать измерения датчика выбранного помещения от новых к старым.

Пункт 0 завершает программу. ID показателей: `temperature`, `humidity`,
`leak`. Для протечки 0 означает отсутствие, 1 — обнаружение; норма 0
фиксирована. Учебные начальные нормы: 18–24 °C и 40–60%.
Границы включены в норму. Это демонстрационные пороги, не универсальные нормативы.

Статусы: **НОРМА**, **ПРЕДУПРЕЖДЕНИЕ**, **АВАРИЯ**, **НЕТ ДАННЫХ**.
Протечка имеет приоритет над отклонениями микроклимата. Отключённый или
разряженный датчик не создаёт измерений; отчёт получает НЕТ ДАННЫХ.
Заряд ниже 20% вызывает рекомендацию обслуживания, но не меняет статус.
Отклонение влажности выводится в процентных пунктах, температуры — в °C.

Изменения порогов действуют только на следующие проверки. У `Reading` и
`MetricAnalysis` остаются границы на момент измерения. `Report` сохраняет
тогдашнее название помещения, активность и заряд датчика, даже если связанные
объекты позже изменились. После сохранения и загрузки эти снимки сохраняются.

### JSON, совместимость и ошибки

Формат файлов ПР2 сохранён: JSON содержит обычные значения и идентификаторы
связанных сущностей. Внутреннее устройство Python-объектов в файлы не попадает.

- `load_data()` читает файлы; `decode_data()` создаёт помещения и показатели,
  затем датчики, отчёты и измерения, восстанавливая ссылки по ID.
- `save_data()` вызывает `encode_data()`: например, `sensor.room` становится
  полем `room_id`, а `reading.metric` — полем `metric_id`.
- `validate_data()` проверяет уникальность ID, поля объектов, общие ссылки,
  соответствие отчётов и измерений. Неизвестные связи не принимаются.
- Повреждённые даты, статусы, неполные отчёты и противоречивые показания
  отклоняются с `ValueError`. Интерфейс выводит понятное сообщение.

Пути вычисляются относительно `main.py`, независимо от папки запуска.
При полном отсутствии данных создаётся пустой проект со справочником.
Если отдельных файлов нет, `migrate_legacy()` читает прежний `state.json`,
выделяет датчики и восстанавливает измерения из истории. Исходный файл
не изменяется. При наличии новых файлов старый файл не используется.
Неполный набор новых файлов считается ошибкой, а не поводом удалить данные.

Запись выполняется через временные файлы с резервным журналом
`.save-backup.json`. При ошибке восстанавливается предыдущее состояние;
после прерывания процесса восстановление выполняется при следующей загрузке.
Если восстановление не удалось, журнал остаётся для повторной попытки.
Изменения в памяти принимаются только после успешного сохранения: действие
меню выполняется над `deepcopy(ProjectData)`, сохраняющей общие ссылки внутри копии.
Программа рассчитана на один запущенный экземпляр.

### Установка и запуск в Windows PowerShell

Требуется Python 3.10 или новее. Из папки проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

При наличии команды `py` окружение можно создать через `py -3 -m venv .venv`.
Консольная часть использует стандартную библиотеку. Веб-части нужен Django;
pytest и flake8 нужны для проверок.

### Тестирование

```powershell
.\.venv\Scripts\python.exe -m pytest -v
.\.venv\Scripts\python.exe -m flake8 .
```

Тесты проверяют конструкторы, методы и строковое представление объектов,
поиск и сортировку, правила мониторинга, исторические снимки, JSON и
восстановление общих ссылок. Сохранены проверки миграции, отката записи,
восстановления после прерывания и сценария меню с повторным запуском.
Файловые тесты используют временные каталоги, не меняя данные проекта.

Аннотации описывают объекты и коллекции. flake8 проверяет стиль и типичные
ошибки кода; сам по себе он не заменяет проверку типов.

## Основные функции полного сервиса (планируются)

Следующие возможности описывают развитие учебной версии ПР3 до полного сервиса.
* **Управление объектами:** расширенное редактирование и иерархическая структура помещений.
* **Мониторинг оборудования:** подключение реальных датчиков и отслеживание их статуса в реальном времени.
* **Сбор и визуализация данных:** автоматический сбор показателей и построение исторических графиков (дашборды).
* **Система алертинга:** настройка пороговых значений и отправка уведомлений (Telegram, Email, SMS) при выходе показателей за пределы нормы или потере связи с датчиком.
* **Аналитика и отчетность:** формирование сводных отчетов по соблюдению норм микроклимата за выбранный период.
* **API и интеграции:** предоставление REST/MQTT API для приема данных со сторонних устройств и выгрузки в внешние системы.

### Этап 1: MVP (Минимально жизнеспособный продукт)
* Реализация базы данных и базового CRUD для основных сущностей.
