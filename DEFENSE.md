# SmartSpace Monitor: защита ПР3

## Что сделано

Проект ПР2 продолжен без замены предметной области. Вместо списков словарей
используются объекты Room, Sensor, Metric, Reading и Report. Их коллекции
находятся в ProjectData. Существующие JSON-файлы и пользовательские сценарии
сохранены. Переписаны операции над сущностями и автоматизированные тесты.

## Класс, объект, конструктор, атрибут и метод

Класс описывает данные и поведение. `Room(1, "Архив", 2, 40)` создаёт
конкретный объект. `room.name` — его атрибут, `room.is_on_floor(2)` — метод.
`self` обозначает объект, для которого вызван метод.

У Room, Sensor, Metric и Reading конструктор `__init__` написан явно.
Он назначает атрибуты и проверяет допустимость состояния. Неверные значения
вызывают ValueError; такой объект не добавляется в коллекцию.

`__str__` возвращает строку и ничего не печатает. Когда меню выполняет
`print(sensor)`, Python получает эту строку через `sensor.__str__()`.
Пять основных сущностей имеют собственные строковые представления.

## Разделение ответственности

- Room знает свои поля и может проверить этаж.
- Sensor знает своё помещение, активность, заряд и доступность.
- Metric хранит нормы, проверяет их изменение и анализирует значение.
- Reading связывает Sensor и Metric, хранит историческую норму и статус.
- Report связывает проверку с Room и хранит снимок результата.
- Функции `find_rooms`, `sort_rooms`, `add_room` работают с коллекциями.
- `check_room` организует взаимодействие нескольких объектов.
- `storage.py` переводит объекты в формат хранения и обратно.
- `main.py` отвечает за меню, ввод и вывод, `utils.py` — за ввод чисел.

Функции не превращены в методы механически: операция над конкретным
состоянием стала методом, операция над коллекцией осталась функцией.

## Связи объектов и JSON

`reading.sensor.room` — тот же экземпляр Room, который находится в
`data.rooms`. Проверить это можно оператором `is`. Оператор `==` для
наших dataclass сравнивает поля; равенство не гарантирует общий экземпляр.

При сохранении `sensor.room.id` записывается как `room_id`. При загрузке
сначала создаются помещения, потом Sensor получает уже существующий Room.
Аналогично восстанавливаются ссылки Reading на Sensor и Metric.
Отсутствующие ссылки и повторяющиеся ID отклоняются.

`MetricAnalysis` хранит независимый снимок анализа и объявлен с
`frozen=True`. Изменение текущей нормы Metric не меняет старые результаты.
Reading также хранит собственные minimum и maximum. Report хранит старые
название помещения, активность и заряд датчика. Это важно для достоверной истории.

## Принципы ООП и декораторы

Инкапсуляция объединяет данные и поведение в классе. Например,
`Sensor.update_state` проверяет сразу два значения перед изменением;
`Metric.update_limits` не допускает перевёрнутые или бесконечные границы.
Поля доступны публично; для изменения состояния приложение использует методы,
а перед записью повторно выполняется проверка. Защиты от любого внешнего
присваивания публичным полям в этой учебной модели нет.

Полиморфизм позволяет одинаково обращаться к разным типам. `str(room)`,
`str(sensor)` и `str(reading)` используют общий протокол строкового
представления, но каждый объект формирует свою строку.

Наследование позволяет описать специализированный класс на основе общего
и при необходимости переопределить методы. В этой версии нет искусственной
иерархии Sensor → TemperatureSensor: используется один комбинированный датчик,
а сущности связаны ссылками на объекты. Это композиция объектов. При появлении
разных реальных устройств можно обосновать общий интерфейс и подклассы.

`@dataclass` — декоратор стандартной библиотеки. Он добавляет служебные методы,
включая сравнение полей; явно написанный `__init__` не заменяет. Для Report
он создаёт конструктор, вызывающий `__post_init__` с проверкой полей.
`@staticmethod` у Sensor._validate_state обозначает проверку, которой
не нужен конкретный self. Эти декораторы используются по назначению.

## Ошибки и сохранение

Неверные значения вызывают ValueError; проблемы файлов — OSError.
Меню показывает сообщение и продолжает работу. Ошибочный JSON не подменяется
пустыми данными. Действие выполняется над глубокой копией ProjectData;
при ошибке сохранения исходное состояние в памяти остаётся прежним.
Глубокая копия создаётся сразу для всего состояния, поэтому общие ссылки
сохраняются внутри копии. Резервный журнал позволяет откатить прерванную запись.

## Сценарий демонстрации

1. Открыть четыре исходных класса: показать `__init__`, поля и `__str__`.
2. Показать ссылки `Sensor.room`, `Reading.sensor`, `Reading.metric`.
3. Запустить приложение; пунктами 1, 10, 11 показать сущности.
4. Добавить помещение (2), найти его (3), отсортировать (4), отобрать этаж (5).
5. Проверить помещение (7); открыть отчёты (9) и измерения (13).
6. Изменить границы температуры (12), выполнить новую проверку.
   В старых измерениях должны остаться старые границы.
7. Отключить датчик (6), повторить проверку: НЕТ ДАННЫХ, новых измерений нет.
8. Проверить все помещения (8), перезапустить программу и показать историю.
9. Открыть JSON: связи сохранены через ID; показать `decode_data` и `encode_data`.
10. Запустить pytest и flake8 командами из README, показать коммит PR3.

Демонстрация изменяет учебные данные. Для репетиции с исходной историей
можно использовать отдельную копию проекта.
